# Policy Bundles (OPA)

Policy bundles let a domain store versioned sets of policy files for an
external policy engine - [Open Policy Agent](https://www.openpolicyagent.org/)
(Rego) - in ZMS, and have ZTS serve
them to authorized workloads. Athenz does not evaluate the bundle content:
ZMS stores, versions, audits and signs it; ZTS verifies and serves it;
the engine running next to the service enforces it. Identity and role data
still come from Athenz tokens and certificates.

The Athenz assertion engine, ZPE and ZPU are not affected.

## Object model

A policy bundle `sports:bundle.api` has:

| attribute         | description                                                                    |
|-------------------|--------------------------------------------------------------------------------|
| `engine`          | `rego`                                      |
| `files`           | list of `{path, content}`; ZMS computes the `sha256` digest of each file       |
| `roots`           | optional OPA manifest roots (default: `<domain>/<bundle>` with `.` → `/`)      |
| `version`         | version name (default `0`); exactly one version is active                      |
| `active`          | set by the server; indicates whether this version is the active one            |
| `description`     | optional description                                                           |

The unit of versioning is the bundle, not the file, since OPA activates a
bundle atomically.

### File rules

| engine  | allowed files                                                                          |
|---------|----------------------------------------------------------------------------------------|
| `rego`  | `*.rego`, `data.json` (any directory)                                                  |

For all engines: paths are relative (`a/b/c.rego`), each segment must match
`[a-zA-Z0-9_][a-zA-Z0-9_.-]*` (no `..`, no hidden files such as `.manifest`),
the top level `athenz/` directory is reserved for files generated by ZTS,
`data.json` must be valid JSON, a bundle needs at least one `.rego` file, and
the file count / file size / bundle size limits apply. Roots must be
slash separated names matching `[a-zA-Z0-9_][a-zA-Z0-9_-]*` and must be within
the domain namespace (the domain name with `.` replaced by `/`, e.g. `sports`
or `sports/api` for domain `sports`). `data.yaml` is not supported - convert it to `data.json` in CI.

ZMS does not compile Rego in-process. Engine
specific validation can be added with a `PolicyBundleValidatorFactory`
plugin (`athenz.zms.bundle_validator_factory_class`) with
`athenz.zms.bundle_validation_mode=off|warn|enforce` (default `enforce`). OPA refuses a
non-compiling bundle at activation and keeps serving the previous one, so
the failure mode without a validator is "no change", not "fail open".

## Managing bundles

The usual Athenz authorization applies. The resource is
`<domain>:bundle.<bundle>`:

| operation                                              | action              |
|--------------------------------------------------------|---------------------|
| get bundle, get bundle version, get all bundles        | `zms.getbundle`     |
| create/update bundle, add file, new version, activate  | `zms.updatebundle`  |
| delete bundle, file or version                         | `zms.deletebundle`  |

Listing bundle names and bundle version names only requires an authenticated
principal. The get-all-bundles api is authorized against `<domain>:bundle.*`.

Domain administrators can do everything. Each domain is limited to
`athenz.zms.quota_bundle` bundles and each bundle to
`athenz.zms.max_bundle_versions` versions. Setting the active
version requires the same `zms.updatebundle` action as any other change.

Using zms-cli:

```
zms-cli -d sports add-bundle api rego authz.rego regions/data.json
zms-cli -d sports show-bundle api
zms-cli -d sports show-bundle api 2
zms-cli -d sports list-bundle
zms-cli -d sports list-bundle-versions api
zms-cli -d sports add-bundle-file api authz.rego
zms-cli -d sports delete-bundle-file api regions/data.json
zms-cli -d sports add-bundle-version api 2 rego authz.rego regions/data.json
zms-cli -d sports copy-bundle-version api 3 2
zms-cli -d sports set-active-bundle-version api 2
zms-cli -d sports delete-bundle-version api 0
zms-cli -d sports delete-bundle api
```

`add-bundle` and `add-bundle-version` replace the files of the (active or
given) version, `add-bundle-file` adds or replaces one file in the active
version, `delete-bundle-file` removes one file from the active version (a
bundle must keep at least one policy file), and `copy-bundle-version` creates a new non-active version from an
existing one (the active version by default). Files are given as `local_path[=bundle_path]`, e.g.
`build/authz.rego=sports/api/authz.rego`.

The ZMS REST API (`/zms/v1/domain/{domain}/bundle/...`) and the generated
Java and Go clients expose the same operations. All changes are audit logged
and update the domain modification timestamp, so ZTS picks them up through
the normal domain sync.

## Signing and sync

ZMS includes the policy bundles in the signed domain data as
`policyBundles`, so they are covered by the regular domain signature. Each
file carries its SHA-256 digest. Rollout order: schema update, ZMS, ZTS, then
point OPA at the new endpoint.

After the domain signature is validated, ZTS verifies the SHA-256 digest of
every file against its content and caches the active versions. A bundle that
fails verification is skipped (and counted in the `bundle_validation_failure`
metric); the rest of the domain data is still processed.

## Fetching bundles from ZTS

The caller must be authorized for the `zts.getbundle` action on the resource
`<domain>:bundle.<bundle>`. Grant it with a regular Athenz role and policy,
e.g. action `zts.getbundle`, resource `sports:bundle.api`, to the role that
contains the workload services.

| endpoint                                               | response                                      |
|--------------------------------------------------------|-----------------------------------------------|
| `GET /zts/v1/domain/{domain}/bundle/{bundle}`          | OPA bundle archive (`application/gzip`)       |
| `GET /zts/v1/domain/{domain}/bundles?engine=rego`      | bundles the caller is authorized to fetch     |

The archive response carries an `ETag` (the bundle revision, i.e. its last
modification time) and honors `If-None-Match`, so steady-state polls return
`304`. The list returns `domain`, `name`, `engine`, `version` and `revision`
of each bundle the caller may fetch.

The archive contains the bundle files and:

* `.manifest` - `revision`, `roots` and `metadata` (`engine`, `domain`, `bundle`, `version`);
* `.signatures.json` - OPA bundle signature (JWT over the file digests with a `scope` claim of `<domain>:bundle.<bundle>`; configure the matching `scope` in the OPA bundle verification config) signed with the ZTS JSON web object key (`athenz.zts.bundle_signing_enabled`, default `true`);
* `<first_root>/athenz/zts/keys/data.json` - optional ZTS JWKS for offline token verification in Rego (`athenz.zts.bundle_include_jwks`, default `false`).

For `rego` bundles the archive is a standard OPA bundle. OPA configuration
using the workload's SIA certificate:

```yaml
services:
  zts:
    url: https://zts.athenz.example/zts/v1
    credentials:
      client_tls:
        cert: /var/lib/sia/certs/sports.api.cert.pem
        private_key: /var/lib/sia/keys/sports.api.key.pem

keys:
  zts-bundle-key:
    algorithm: ES256
    key: |
      -----BEGIN PUBLIC KEY-----
      ...ZTS public key...
      -----END PUBLIC KEY-----

bundles:
  sports-api:
    service: zts
    resource: domain/sports/bundle/api
    polling: {min_delay_seconds: 30, max_delay_seconds: 120}
    signing: {keyid: zts-bundle-key}
```

With the default roots (`sports/api`) the Rego modules use
`package sports.api...` and data files live under `sports/api/`.

## Configuration

Policy bundle support is disabled by default. While disabled, every policy
bundle endpoint in ZMS rejects the request right away with a 400 error
(`Policy bundle support is not enabled`).

ZMS (`zms.properties`):

| Property | Default | Description |
|---|---|---|
| `athenz.zms.bundle_enabled` | `false` | Enables policy bundle support. When `false`, all policy bundle endpoints reject requests with a "not enabled" error. Dynamic: can be changed at runtime. |
| `athenz.zms.bundle_engines` | `rego` | Comma separated list of policy engines domains may use. |
| `athenz.zms.quota_bundle` | `20` | Default number of policy bundles allowed per domain. |
| `athenz.zms.max_bundle_versions` | `5` | Maximum number of versions per bundle. |
| `athenz.zms.max_bundle_files` | `100` | Maximum number of files in a bundle. |
| `athenz.zms.max_bundle_file_size` | `1048576` | Maximum size in bytes of a single file. |
| `athenz.zms.max_bundle_size` | `4194304` | Maximum total size in bytes of all files in a bundle. |
| `athenz.zms.max_bundle_roots` | `16` | Maximum number of OPA manifest roots in a bundle. |
| `athenz.zms.bundle_validator_factory_class` | none | Optional `PolicyBundleValidatorFactory` class used to validate bundle content (e.g. compile rego). Structural per-engine rules are always enforced. |
| `athenz.zms.bundle_validation_mode` | `enforce` | Action when the validator reports an error: `off`, `warn` (log only) or `enforce` (reject). |

Add `bundle` to `athenz.zms.audit_ref_check_objects` to require audit
references for bundle changes in audit-enabled domains.

ZTS (`zts.properties`): `athenz.zts.bundle_signing_enabled`,
`athenz.zts.bundle_include_jwks`, `athenz.zts.bundle_cache_size` (generated archives kept in memory).

Schema: `servers/zms/schema/updates/update-20261105.sql` adds the
`policy_bundle` and `policy_bundle_file` tables.
